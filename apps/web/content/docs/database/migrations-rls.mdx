Las migraciones son el historial operativo del esquema. Cada archivo transforma
una base existente hasta el siguiente estado sin reconstruirla desde cero y sin
depender de pasos manuales fuera del control de versiones.

## Principios de migración

Las migraciones históricas ya aplicadas no se editan. Si hay que corregir una
tabla, función, política, índice o tipo, se agrega una migración nueva que lleve
el estado anterior al estado esperado. Esto mantiene trazabilidad entre local,
preview y producción.

Una migración puede crear tablas, agregar columnas, actualizar RPCs, cambiar
permisos, habilitar RLS o ajustar contratos que consume el frontend. Si cambia la
forma de una respuesta SQL, también hay que revisar los tipos y hooks que la
consumen.

## Qué protege RLS

Row Level Security define qué filas puede leer o modificar cada tipo de cliente.
El frontend usa credenciales públicas, y la autenticación de la app se administra
con Better Auth en el schema `better_auth`. El perfil de la app vive en
`public."user"` y referencia a `better_auth."user"`.

### Catálogos académicos

Tablas como `campus`, `academic_unit`, `study_plan`, `course`, `professor` y las
tablas de oferta pueden leerse desde el cliente porque alimentan onboarding,
mallas, búsqueda y horarios. Esa lectura no implica escritura: los cambios del
catálogo se hacen por migraciones, seeds o procesos de sincronización (`data/itcr`) con credenciales
elevadas.

```sql title="Lectura pública filtrada"
CREATE POLICY "Lectura pública de cursos activos"
ON public.course
FOR SELECT
TO anon, authenticated
USING (is_active = true);
```

### Datos del usuario

`public."user"`, `user_study_plan`, `student_course_record`, `saved_schedule` y
`saved_schedule_item` contienen datos privados. Las políticas deben validar que la
fila pertenece al usuario actual o que la operación se ejecuta con un rol
administrativo autorizado.

```sql title="Datos propios"
CREATE POLICY "Usuario ve sus registros"
ON public.student_course_record
FOR SELECT
TO authenticated
USING (user_id = (select auth.uid()));
```

En tablas hijas se valida la propiedad a través de la tabla padre:

```sql title="Propiedad heredada"
CREATE POLICY "Usuario ve items de sus horarios"
ON public.saved_schedule_item
FOR SELECT
TO authenticated
USING (
  EXISTS (
    SELECT 1
    FROM public.saved_schedule s
    WHERE s.id = saved_schedule_id
      AND s.user_id = (select auth.uid())
  )
);
```

### Contenido comunitario

Las reseñas y evaluaciones tienen una vista pública cuando están aprobadas, una
vista propia para quien las envía cuando aplica, y una vista administrativa para
moderación. `professor_review`, `professor_review_reaction`,
`professor_review_report`, `course_evaluations` y `user_role` combinan políticas
públicas, privadas y administrativas.

```sql title="Moderación con rol interno"
CREATE POLICY "Administradores ven reportes"
ON public.professor_review_report
FOR SELECT
TO authenticated
USING (public.is_admin());
```

## Modelo de seguridad y roles (Cloudflare Hyperdrive)

La arquitectura de conexión de producción desacopla la autenticación del pooler y la
gestión de privilegios mediante el **Group Role Pattern** de PostgreSQL, asegurando el
principio de mínimo privilegio (_least privilege_).

### Patrón de roles grupales (`hyperdrive_role`)

En lugar de otorgar permisos directamente a usuarios de login individuales, se define
un rol de grupo no autenticable (`NOLOGIN`):

```sql title="Definición del rol grupal hyperdrive_role"
CREATE ROLE hyperdrive_role NOLOGIN;
ALTER ROLE hyperdrive_role BYPASSRLS;

-- Permisos estrictamente DML y ejecución (sin privilegios DDL ni DROP)
GRANT USAGE ON SCHEMA public, better_auth, extensions TO hyperdrive_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public, better_auth TO hyperdrive_role;
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA public, better_auth TO hyperdrive_role;
GRANT EXECUTE ON ALL ROUTINES IN SCHEMA public, better_auth, extensions TO hyperdrive_role;
```

El usuario de conexión utilizado por Cloudflare Hyperdrive (`hyperdrive_user`) hereda los
permisos de este grupo mediante `GRANT hyperdrive_role TO hyperdrive_user;`.

### Riesgos de la guía rápida de Cloudflare (`GRANT postgres`)

La documentación genérica de Cloudflare Hyperdrive suele sugerir vincular el usuario
con `GRANT postgres TO hyperdrive_user;`. En Supabase o PostgreSQL estándar, este
enfoque introduce vulnerabilidades críticas:

1. **Privilegios de superusuario/owner**: Concede control total para ejecutar DDL
   destructivo (`DROP TABLE`, `ALTER TABLE`, `DROP DATABASE`), alterar esquemas y
   manipular extensiones o configuraciones globales del motor.
2. **Violación de mínimo privilegio**: Una inyección SQL accidental o bug en la capa de
   la aplicación podría destruir esquemas completos o crear roles con privilegios
   elevados.
3. **Falta de auditoría granular**: Impide separar las operaciones automatizadas de
   migración (ejecutadas por `postgres`) del tráfico operacional DML generado por el
   Worker.

`hyperdrive_role` restringe el acceso exclusivamente a operaciones DML (`SELECT`,
`INSERT`, `UPDATE`, `DELETE`) y ejecución de rutinas, impidiendo cualquier operación
DDL o de administración de base de datos desde la API.

### Privilegios por defecto (`ALTER DEFAULT PRIVILEGES`)

Al aplicar nuevas migraciones con el usuario `postgres`, las tablas o rutinas recién
creadas pertenecen a `postgres` sin permisos de acceso para `hyperdrive_role`, lo que
históricamente requería _hotfixes_ manuales de permisos tras cada migración.

Para resolver esto de forma preventiva y determinista, se configuran privilegios por
defecto para todos los objetos futuros creados por el rol `postgres`:

```sql title="Configuración de privilegios por defecto"
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO hyperdrive_role;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO hyperdrive_role;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  GRANT EXECUTE ON ROUTINES TO hyperdrive_role;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA better_auth
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO hyperdrive_role;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA better_auth
  GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO hyperdrive_role;
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA better_auth
  GRANT EXECUTE ON ROUTINES TO hyperdrive_role;
```

Cualquier tabla, vista, secuencia o función creada en migraciones subsecuentes queda
inmediatamente disponible para el Worker sin intervención manual.

### Justificación de `BYPASSRLS` en la arquitectura

El atributo `BYPASSRLS` en `hyperdrive_role` es apropiado y seguro bajo el diseño
actual de la plataforma por dos motivos fundamentales:

1. **Eliminación del PostgREST público**: El acceso directo de Supabase para los roles
   `anon` y `authenticated` ha sido revocado (migración `0143`). Ningún cliente web
   puede consultar la base de datos directamente vía REST o GraphQL sin pasar por el
   Cloudflare Worker.
2. **Autorización en la capa de aplicación (Better Auth + Effect)**: Toda petición es
   recibida, autenticada y autorizada en el Cloudflare Worker mediante Better Auth y
   servicios de Effect TS antes de consultar PostgreSQL. RLS a nivel de base de datos se
   diseñó para clientes HTTP directos que pasan JWTs de Supabase (`auth.uid()`); al
   centralizar la lógica de negocio y las verificaciones de permisos en Effect, el Worker
   actúa como un servicio backend confiable de alto rendimiento que realiza consultas
   directas parametrizadas.

## RPCs como contratos

Muchas pantallas no consumen tablas directamente. Usan RPCs que encapsulan joins,
filtros, agregaciones y reglas de negocio. Una RPC puede ser el contrato real del
frontend aunque la tabla subyacente tenga muchas más columnas.

Las funciones `SECURITY DEFINER` deben validar identidad o rol dentro del cuerpo y
definir `SET search_path` con el schema mínimo necesario. Esto evita que el
resultado dependa del contexto de quien invoca la función y reduce riesgos de
resolución ambigua de nombres.

```sql title="SECURITY DEFINER seguro"
CREATE OR REPLACE FUNCTION public.get_moderation_queue()
RETURNS SETOF professor_review
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  IF NOT public.is_admin() THEN
    RAISE EXCEPTION 'forbidden' USING ERRCODE = '42501';
  END IF;

  RETURN QUERY
  SELECT *
  FROM public.professor_review
  WHERE status = 'pending'::professor_review_status;
END;
$$;
```

## Cambios que afectan al frontend

Si una migración agrega, elimina o cambia columnas que consume la UI, hay que
revisar los clientes TypeScript. En este proyecto los puntos de entrada más
importantes son `src/lib/api.ts`, `src/lib/hooks/use-queries.ts`,
`src/lib/evaluations/api.ts` y `src/lib/professor-reviews/api.ts`.

Cambios en enums requieren revisar labels, filtros y ramas de UI. Cambios en RLS
requieren revisar si la pantalla corre como anónimo, autenticado o admin. Cambios
en RPCs requieren revisar firma, permisos, `search_path`, tipos de retorno y
consumidores.

## Flujo para aplicar migraciones

```bash title="Aplicar migraciones locales"
pnpm run db:migrate
```

```bash title="Aplicar migraciones en producción"
pnpm run db:migrate -- --prod
```

Estos comandos aplican migraciones pendientes sin borrar datos. No se debe usar
reset para aplicar cambios normales: un reset elimina información local o remota y
puede ocultar una migración mal definida.

## Checklist

- La migración transforma una base existente sin requerir reset.
- Las migraciones históricas permanecen intactas.
- Tablas nuevas tienen PK, FKs, constraints e índices mínimos.
- RLS distingue lectura pública, datos propios y administración.
- Funciones `SECURITY DEFINER` validan identidad o rol y definen `search_path`.
- Cambios de RPC mantienen o documentan el contrato del frontend.
- Enums visibles tienen representación en la UI.
- Columnas nuevas consideran backfill, defaults, nullability e índices.
- Cambios en datos sync-managed consideran `is_active`, `updated_at` y
  `deactivated_at`.
- Privilegios por defecto (`ALTER DEFAULT PRIVILEGES`) para `hyperdrive_role`
  cubren nuevos objetos.
