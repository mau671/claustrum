---
title: Extracción de datos del ITCR
description: Flujo actual de descarga, procesamiento, generación SQL y sincronización idempotente desde fuentes externas.
---

El pipeline vive en `supabase/tec-data/`. Es una CLI de Python empaquetada con
`uv` que descarga datos del ITCR, los normaliza a archivos `data/raw/**/data.json`
y genera seeds SQL para Supabase.

El flujo actual trabaja por alcance lógico (`scope`), no por una bandera
`--entity`. Los alcances válidos son:

| Scope      | Incluye                                                                    |
| ---------- | -------------------------------------------------------------------------- |
| `catalog`  | Catálogo institucional, periodos, planes, cursos y relaciones.             |
| `offering` | Profesores, ofertas, grupos, profesores por grupo y reuniones.             |
| `all`      | Catálogo + oferta. Es el reemplazo de cualquier alcance histórico `mixed`. |

## Comandos principales

```bash title="Instalación"
cd supabase/tec-data
uv sync
```

```bash title="Pipeline recomendado"
uv run tec-data pipeline --scope catalog --years 2026
uv run tec-data pipeline --scope offering --years 2026
uv run tec-data pipeline --scope all --years 2026
```

`pipeline` orquesta `download + process` respetando dependencias. Para `offering`,
si faltan archivos procesados de catálogo (`campus`, `academic_unit`,
`academic_term`, `course`) o términos del año solicitado, prepara primero el
catálogo completo. `--skip-download` permite reprocesar archivos ya descargados.

```bash title="Etapas manuales"
uv run tec-data download --scope catalog
uv run tec-data process --scope catalog --years 2026
uv run tec-data download --scope offering --years 2026
uv run tec-data process --scope offering --years 2026
```

La descarga de planes acepta `--concurrency` para controlar cuántas consultas de
detalle corren en paralelo. La oferta requiere `--years` porque los endpoints del
TEC se consultan por año.

## Fuentes y mezcla

El catálogo usa endpoints de `tecdigital.tec.ac.cr` y `tec-appsext.itcr.ac.cr`
para sedes, unidades académicas, modalidades, periodos y planes. El procesamiento
de planes genera `study_plan`, `study_plan_campus`, `study_plan_level`, `course`,
`study_plan_level_course` y `course_relation`.

La oferta académica se construye mezclando dos fuentes por año:

| Fuente local           | Origen                                    | Uso principal                              |
| ---------------------- | ----------------------------------------- | ------------------------------------------ |
| `course_offer/{year}`  | Oferta por escuela/año                    | Horas, periodo, sede y metadatos de curso. |
| `schedule_guia/{year}` | Guía de horarios por sede/carrera/periodo | Grupos, días, horas, aula y profesores.    |

La mezcla produce `course_offering`, `course_offering_group`,
`course_offering_group_professor`, `course_offering_meeting` y `professor`. Los
nombres placeholder como `SIN PROFESOR ASIGNADO` no se insertan como profesores.
Las aulas vacías o `NO DISPONIBLE` se convierten en `NULL`.

## Generación SQL

```bash title="Generar seed delta"
uv run tec-data sql --scope all --years 2026 --manifest
```

Por defecto `tec-data sql` genera un seed versionado en
`../seeds/tec-data/seed_YYYYMMDDTHHMMSSZ.sql`. También puede emitir un archivo
puntual con `--mode full --output ../seed.sql`.

El generador SQL usa `INSERT ... ON CONFLICT DO UPDATE` contra llaves naturales y
reactiva filas sincronizadas (`is_active = true`, `deactivated_at = null`). Para
oferta, los soft deletes se limitan a los términos sincronizados. Para catálogo,
solo se desactivan tablas incluidas en el scope de la corrida.

## Sync unificado

```bash title="Sync local/remoto"
uv run tec-data sync --target local --years 2026
uv run tec-data sync --target remote --years 2026 --env-file ../../.env.production.local
uv run tec-data sync --target db-url --db-url "postgresql://..." --years 2026
```

`sync` es el flujo operativo principal. Ejecuta el pipeline, remapea IDs contra
la base destino, genera un delta mínimo, escribe un manifest JSON y, salvo
`--no-apply`, aplica el seed.

El remapeo consulta la base por llaves naturales: `campus.code`,
`academic_unit.code`, `academic_term.external_key`, `course.code`,
`professor.full_name`, `study_plan` por `(unidad, external_plan_id)`, oferta por
`(curso, sede, unidad, periodo)` y así sucesivamente. Si la fila ya existe, se
reutiliza su ID real; si no existe, se asigna el siguiente ID secuencial positivo
para esa tabla. Esto conserva referencias históricas y evita depender de hashes
deterministas.

Cada seed generado incluye metadata estricta en cabecera y manifest:

| Campo                | Propósito                                           |
| -------------------- | --------------------------------------------------- |
| `environment_id`     | Identifica host/proyecto/base destino.              |
| `scope`              | `catalog`, `offering` o `all`.                      |
| `years`              | Años incluidos en la corrida.                       |
| `term_external_keys` | Términos afectados por la corrida.                  |
| `data_fingerprint`   | Hash del payload normalizado para detectar cambios. |
| `table_stats`        | Inserciones, updates y soft deletes por tabla.      |
| `noop`               | Indica que no hubo cambios de datos.                |

Si el fingerprint ya fue aplicado para el mismo scope/años/términos, `sync`
genera un seed NOOP de auditoría y no vuelve a aplicar datos.

## Seed history

```bash title="Generar delta desde historial"
uv run tec-data sync \
  --target seed-history \
  --seed-dir ../seeds/tec-data \
  --scope offering \
  --years 2026 \
  --no-apply
```

`seed-history` reconstruye el estado esperado aplicando migraciones y replayeando
los seeds históricos en una base PostgreSQL efímera. En CI usa un service
container; localmente puede levantar un contenedor temporal. Este modo no escribe
en `sync_seed_run` porque su propósito es producir un nuevo delta versionado para
revisar o subir en PR.

## Ledger de seeds

Los seeds aplicados a entornos reales se registran en `public.sync_seed_run`.
La tabla guarda `seed_file_name`, `seed_sha256`, `scope`, `years`,
`term_external_keys`, timestamps de generación/aplicación, `status` y metadata
JSON. Los scopes válidos son `catalog`, `offering` y `all`; los estados válidos
son `generated`, `applied`, `failed` y `skipped_duplicate`.

## CI operativo

El workflow `.github/workflows/catalog-artifact.yml` genera un artifact con el
catálogo procesado. El workflow `.github/workflows/generate-seed.yml` reutiliza
ese artifact, valida que esté completo y ejecuta `sync --target seed-history
--scope offering --years 2026 --no-apply`. Si el manifest no es NOOP, crea un PR
con los nuevos seeds en `supabase/seeds/tec-data`.

## Implementación

La CLI está organizada por capas:

| Ruta                      | Responsabilidad                                           |
| ------------------------- | --------------------------------------------------------- |
| `src/app/cli.py`          | Entrada Typer y comandos públicos.                        |
| `src/workflows/`          | Orquestación de descarga, procesamiento, pipeline y sync. |
| `src/infra/tec_api/`      | Clientes HTTP para endpoints del TEC.                     |
| `src/domains/catalog/`    | Procesamiento de catálogo base.                           |
| `src/domains/study_plan/` | Procesamiento de planes, cursos y relaciones.             |
| `src/domains/offering/`   | Mezcla de oferta, grupos, reuniones y profesores.         |
| `src/domains/sync/`       | Generación SQL, remapeo, fingerprint y helpers de seed.   |

## Consideraciones operativas

No se debe resetear la base para aplicar cambios normales. El pipeline está
diseñado para correr de forma idempotente sobre datos existentes, preservando IDs
cuando las llaves naturales coinciden y usando soft delete para datos que dejan de
aparecer en la fuente. Para producción, usa primero `--no-apply --keep-sql` si se
necesita revisar manualmente el delta.
